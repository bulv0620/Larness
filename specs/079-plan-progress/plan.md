# 实施计划：计划步骤即时更新

> 用户已确认方向 A + B（2026-11-16）：先写红测试，再实现提示层与运行时提醒。

## 1. 顺序

1. **PG-1 诊断复核**：用只读查询统计每轮 `plan.updated` 次数与时间点，确认「链路无丢失、模型只在首尾更新」。
2. **PG-2 提示层（A）**：改写 `SYSTEM_POLICY` 计划条款与 `update_plan` 描述，升 `PROMPT_VERSION`；红测试断言实际组装的系统提示与工具描述。
3. **PG-3 运行时提醒（B）**：新增 `turn/planReminder.ts` 纯函数；Runner 统计「距上次计划更新的工具调用数」，超阈值注入一次提醒并在计划更新后复位；红测试覆盖触发、不重复、不打扰。
4. **PG-4 验证与收口**：`app test/agent` 全量、`pnpm check`、`pnpm build`；回填 `tasks.md`、`STATUS.md`、`ROADMAP.md`。

## 2. 设计要点

- 计数按**工具调用**而非模型步数：一步可并行多个工具调用，按步计数会让一轮里极少触发。
- 计数在工具执行前自增，`update_plan` 处理器内部复位，避免「先复位再自增」把计费留在 1。
- 提醒注入点复用既有机制（`messages.push({ role: "user", content })`），与项目锁提示、预算收尾提示、重复失败提示同一位置（每步请求前）。
- 每个计划版本只提醒一次（`planReminderSent`），避免对固执的模型反复消耗 token。
- 提醒不写事件、不落库，因而对重放与前端零影响。

## 3. 不改动

- `PlanParamsSchema`、状态别名归一化、`plan.updated` 事件形状、前端 reducer 与时间线。
- Turn 预算、审批、项目锁、秘密检查。
- 不做服务端自动勾完（违反 036 的取消/失败语义）。

## 4. 风险

| 风险 | 处置 |
|---|---|
| 提醒成为噪声，模型每步都被催 | 每计划版本一次 + 有界文本（≤5 个步骤） |
| 提醒被理解成「把剩余步骤标 done」 | 文本明确「完成且已验证才标 done」，并有测试断言 |
| 阈值过高无效 / 过低浪费 | 取 6，记入 Q-039 待真实长任务观察后调整 |
| 系统提示变化影响缓存 | `PROMPT_VERSION` 升版，使失效可解释 |
