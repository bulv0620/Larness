# M4-0 全局 PM2 与退出恢复实验

2026-11-06，macOS arm64，Node.js 20.19.3、npm 11.5.2、PM2 7.1.2。使用 `pnpm test:poc:m4` 复跑。命令需要 npm registry 网络，在临时目录以全局模式安装固定候选版本。常规测试保留离线运行路径。

| 实验 | 实测结果 |
|---|---|
| P1 全局安装 | 首次缺失后用 `npm install --global --prefix <临时目录>` 安装。再次初始化复用同一入口，未改动文件时间，也未启动守护。覆盖 npm 缺失、目录不可写、registry 不可达后重试、已装版本不兼容和入口符号链接越界。真实全局 prefix 未写入。 |
| P2 实例隔离 | 两个私有 `PM2_HOME` 同时托管同名服务。分别验证版本、日志、启停和健康。拒绝无登记、目录或 socket 符号链接，以及登记版本与 PM2 启动参数不符。对一个实例执行停止，另一个实例的进程和健康保持不变。 |
| P3 正常退出、崩溃与重开 | 走真实 TUI 的 `runManagedSessions` 和开发 supervisor，启动实际 Server 和 Vite。正常退出后管理端口、IPC token 和锁清理，PM2 服务 PID 和 HTTP 响应不变。下一次启动读取同一实例并核对服务，再向实际 Server 发出 SIGKILL。服务仍保持相同 PID 和 HTTP 健康。第三次启动重新读取磁盘登记和 PM2，得到同一 PID、版本、启动配置与健康。 |
| P4 状态与失败 | 外部进程占用端口时拒绝启动。PM2 报 online 但 HTTP 超时则为 unhealthy，重复启动请求保留同一 PID。应用被强制结束后，PM2 在禁用自动重启时报告 stopped，对账结合期望运行状态识别为 failed。守护失联或 socket 不可信时返回 unknown，读取不会拉起守护。 |
| P5 环境、权限与清理 | 两个实例位于当前用户私有临时目录。客户端及应用未继承测试用的秘密标记，状态查询仅输出核验所需字段，应用日志、守护日志及信号退出写出的 dump 未出现标记。清理仅向已核验的实验守护发送信号，等待退出，移除残留 socket，检查测试监听不可达并删除临时目录。 |

## 接入前需明确的边界

- 实验使用固定 PM2 版本的 socket 连接能力。直接使用会自动启动守护的客户端入口无法保持只读语义，后续适配器需保留现存守护的连接路径，并验证版本兼容。应用名与命名空间用于定位，目录、socket、守护身份、已登记版本、启动配置和 HTTP 身份都要核验。验证与实际使用之间仍有同账户修改的窗口，属于应用层约束。
- 正常退出时先让部署到达安全点，再关闭管理面和临时开发资源。M4-0 验证退出和重开路径，正在执行的正式部署及其安全点由后续任务验证。重开时以持久登记约束身份，用实际 PM2 和健康结果刷新观察状态。PoC 使用临时登记文件，产品用数据库与既有授权和事件机制实现。
- PM2 守护收到 SIGTERM 时会写 dump，即使未执行 `pm2 save`。实验使用合成标记验证继承环境隔离。正式 `secretRef` 交付前需验证明文不会落入 PM2 元数据、dump 或日志，见 [Q-029](../../docs/open-questions.md)。[PM2 7.1.2 守护退出实现](https://github.com/Unitech/pm2/blob/v7.1.2/lib/Daemon.js#L325)
- 验证范围为本机 macOS arm64、单进程 fork 服务、loopback HTTP。浏览器服务状态界面、主机重启、系统启动项、跨平台及 PM2 本身升级待对应任务验证。
