# G4 手动验收清单

> 2026-11-07，当前流程按 ADR-050。用户已确认 M4 与后续修改全部验收通过。本清单供复验，见 [M4 收尾](closure.md)。

## 普通项目会话部署

1. 重启 Larness，登记一个实际项目并配置可用模型。在该项目的普通聊天中请求「按项目脚本构建并通过系统 PM2 持久运行，服务名 api；检查实际访问结果」。可以同时补充端口和启动要求。
2. Agent 应从系统上下文得到 Node/PM2 入口、PM2_HOME、项目 ID、发布根和已有服务。它通过文件与命令工具读取脚本、构建、准备运行文件、启动 PM2 并检查访问，不要求先进入运维 Agent 或创建专用发布计划。
3. standard/strict 在命令策略要求时显示真实审批；autonomous 对已授权步骤直接执行。拒绝或取消后查看真实命令结果与 PM2 状态。
4. 打开「服务运维」，核对所属项目、完整 PM2 名称、PID 和观察时间。CLI 进程运行时业务健康默认显示未核验，健康声明以 Agent 的实际访问证据为准。

## 项目关联与操作

- 两个项目分别运行名为 api 的服务，应得到不同完整名称 `larness:<projectId>:api`。同一项目也可运行 web 和 worker。项目重命名后服务继续归属同一个 ID。
- 在运维弹窗点「在项目会话中处理」，应选择对应项目并准备状态检查请求，由用户发送。已有草稿应保留。
- 通过项目会话要求停止或重启指定服务，重新打开运维弹窗核对真实状态。查看有限日志，失败和空内容分别展示。
- 原 `larness-<targetId>` 服务显示旧关联和历史，Agent 应使用已提供的实际名称操作。归属不明或名称冲突的实例服务单独提示。

## 服务运维界面与人工控制（M4-R1）

1. 打开「服务运维」，确认没有“独立于当前聊天”字样。卡片、状态徽标、信息卡和深色日志区应与项目服务窗一致，窄屏/深色模式下无控件遮挡。
2. 从卡片进入详情，核对项目、PM2 完整名称、PID 与日志。停止/重启应先显示准确名称、项目及影响，取消后进程不变。
3. 确认停止后应显示已停止、PID 为空；点击启动后显示实际运行与新 PID；确认重启后 PID 更新。健康未核验不能显示已通过。
4. 操作失败显示提示，观察刷新真实状态；返回服务列表、关闭弹窗不停止服务。「在项目会话中处理」仍选择所属项目并保留草稿。

## 生命周期验证

停止 TUI 后，已交付 PM2 的正式服务继续提供访问。重开后核对实际 PID 和状态。停止/取消单次命令与停止正式服务分别观察，CLI 结果未知时先查询实际状态。主机开机自启尚无支持声明。

## 自动化与边界

本轮必要检查包括实际上下文/命令执行、真实 PM2 两项目部署/停止/日志/退出、原服务兼容、Web 项目会话入口、类型与改动文件检查，结果见 [M4-R0 验收](acceptance-cli.md)。浏览器视觉和真实模型由用户手动验收。Q-029 正式秘密注入、远程 HTTPS、Linux/Windows 和主机重启仍按各自证据范围处理。
