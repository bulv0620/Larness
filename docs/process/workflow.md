# 开发工作流

> 适用于人类与所有编码 Agent。目标：把大设计拆成可验证的小步，任何一步都不破坏已有能力。

## 1. 文档层级

```text
CONSTITUTION.md                 不可协商
  └── docs/adr/DECISIONS.md     已冻结决策
        └── specs/<slice>/      单里程碑 / 单功能
              ├── spec.md       做什么、为什么、验收
              ├── plan.md       怎么做、改哪些文件、如何回滚
              └── tasks.md      可执行任务与状态
docs/architecture|contracts/    跨里程碑稳定知识
```

spec 与契约冲突时，先停，按 `AGENTS.md` 第 9 节提问；不要自行选择一方。

## 2. Spec 生命周期

| 状态 | 含义 | 可否实现 |
|---|---|---|
| `draft` | 只有范围与方向，验收未细化 | 否 |
| `ready` | 目标、验收、契约、风险、任务齐全，依赖已满足 | 是 |
| `active` | 至少一个任务 `in_progress` | 是（仅当前任务） |
| `done` | 所有任务 `done`，门禁通过 | 否（除非新开 spec） |
| `blocked` | 存在未决边界 / 外部依赖 | 否 |

从 `draft` 到 `ready` 的检查：

- [ ] 目标与非目标明确，不与其他 spec 重叠；
- [ ] 至少 3 条可执行的 Given-When-Then 验收场景；
- [ ] 接口 / 数据 / 配置变更已写入 `docs/contracts/*`；
- [ ] 安全、权限、失败与恢复路径已覆盖；
- [ ] 任务拆分到 0.5–2 天粒度，依赖明确；
- [ ] 测试计划包含成功、失败、权限、并发路径；
- [ ] 人类负责人确认（可在任务评论 / 会话中确认）。

## 3. 任务状态机

```text
todo → in_progress → review → done
        │  ↑
        └── blocked
```

- `todo`：依赖未满足或未开始。
- `in_progress`：已认领，必须在 `STATUS.md` 登记。
- `blocked`：写明阻塞原因、需要谁决策、已尝试方案。
- `review`：实现与测试完成，等待人类抽查（涉及 UI / 安全 / 契约时强制）。
- `done`：验收命令通过，文档与状态已更新，已提交。

同一时刻只允许一个 `in_progress` 任务（人类明确并行时除外）。

## 4. 标准执行循环

1. **选择**：`ROADMAP.md` 中依赖全部 `done` 的最小任务；优先修复阻塞其他任务的问题。
2. **上下文**：读 spec / plan / tasks、契约、相关代码；列出 3–7 条实施要点。
3. **测试**：先写失败测试；确认失败信息指向缺失行为，而不是环境问题。
4. **实现**：最小闭环；保持模块边界；不引入未批准依赖。
5. **验证**：任务验收命令 + `pnpm check`；涉及 UI 时附截图；涉及 API 时附 curl / 测试输出。
6. **复查**：对照 spec 的验收场景逐条确认；检查失败路径与权限。
7. **记录**：勾选任务、更新 `STATUS.md`、契约 / ADR / open-questions。
8. **提交**：一个任务一个提交；提交信息带任务 ID。

## 5. 评审门

| 门 | 触发 | 检查人 | 通过标准 |
|---|---|---|---|
| G-Spec | spec `draft → ready` | 人类 | 第 2 节清单 |
| G-Task | 任务 `in_progress → review` | Agent 自检 + 人类抽查 | 验收场景、测试、无越权改动 |
| G-S0 | 视觉 Demo 完成 | 人类 | 文档 7.1 六条 + `D0-9` 清单 |
| G0 | M0 完成 | 人类 | 根文档 42.1 全部通过 |
| G1–G4 | 各里程碑 | 人类 | 对应 `ROADMAP.md` 门禁 |
| G5 | 发布候选 | 人类 | 根文档 42.3 + 发布清单 |

安全 / 认证 / 代理 / 更新相关任务必须经过人类评审，不能仅凭自动化测试放行。

## 6. 分支与提交

```text
main
└── task/d0-1-web-bootstrap
```

- 分支名：`task/<task-id>-<slug>`；修复：`fix/<task-id>-<slug>`。
- 提交：`<type>(<scope>): <summary> (<TASK-ID>)`。
- 一个 PR / 合并只包含一个任务；允许附带该任务的测试、文档、迁移。
- 合并前必须通过 CI；不 force push；不提交构建产物与数据。

## 7. 变更已冻结内容

1. 新建 `docs/adr/ADR-0xx-<slug>.md`（从模板复制），状态 `proposed`。
2. 说明背景、现状、备选方案、影响（PRD / API / DB / 安全 / 迁移）、回滚。
3. 更新 `DECISIONS.md` 索引；在 `STATUS.md` 标记等待决策。
4. 人类批准后改为 `accepted`，同步修改 spec / 契约 / 代码。
5. 被替代的 ADR 标记 `superseded by ADR-0xx`，不删除。

## 8. 完成定义（DoD）

- [ ] 验收场景逐条通过（自动化优先，人工步骤有记录）；
- [ ] 新增 / 修改代码有对应测试，失败路径覆盖；
- [ ] `pnpm check`、`pnpm build` 通过；涉及 E2E 的任务跑 `pnpm test:e2e`；
- [ ] 无新增 `any` / 忽略检查 / 跳过测试；
- [ ] 契约、数据模型、配置、README 已同步；
- [ ] 安全影响已评估，审计与脱敏已覆盖；
- [ ] `tasks.md`、`STATUS.md` 已更新；
- [ ] 已提交，提交信息包含任务 ID。

## 9. 阻塞与升级

- 同一问题两次尝试失败 → `blocked`，附证据与备选方案。
- 需要产品决策 → 提给人类，给出 2–3 个选项与推荐。
- 需要跨任务重构 → 新开任务，不在当前任务中扩大范围。
- 发现安全问题 → 立即停止相关实现，记录复现步骤，按严重度通知人类。

## 10. 时间与范围控制

- 任务实际工作量超过 spec 预估 2 倍时，停止并拆分。
- 不接“顺手优化”；把发现记录为 `todo` 或新任务。
- 里程碑门禁未过，不启动下一里程碑（除非人类明确要求并行）。

## 业务审批与实施门禁（ADR-042，2026-11-05）
完全自主是产品中已授权Agent业务动作免人工审批/确认（包括部署/启停/支持的恢复），不是省略计划/鉴权/锁/审计；人工审批仅当前策略需要时产生。它不自动把draft规格或未通过的PoC变成可实现状态，也不将“更新设计文档”扩大为启动M3/M4代码的授权。产品方向已明确的边界无需反复征询，但技术开放项与实施门禁仍按工作流处理。
